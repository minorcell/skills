# 解说词写作

解说词是唯一的内容源——画面时长由它驱动。改词就能重出片。

## 结构

一段好的入门讲解视频，段落顺序几乎是固定的：

1. **痛点开场**（无章节标签）。用一个观众亲身经历过的场面开局，不要自我介绍、不要「大家好」。
   例：改文档改到一半手一抖删了，第二天找不回来。
2. **概念**——这东西是什么。用**一个生活比喻**讲透。
3. **为什么不用土办法**——列举笨办法的硬伤，3 条，每条一句话。
4. **原理/心智模型**——整集最核心的一段，要明确告诉观众「下面是整集最重要的一段」。
5. **实操**——真机演示，命令逐个敲出来。
6. **常见错误与对策**。
7. **回顾**——用 3-4 句话收束整集，给一句能记住的金句。

## 句子

- **每段 30-60 秒，对应一屏画面。** 超过 60 秒，画面撑不住；低于 25 秒，观众来不及理解。
- **句子要短。** 一句一个意思，句末用 `。！？`——切句粒度直接决定字幕分段和画面节拍节点。
- 中文语速参考：`+8%` 语速下约 **5.5-6.5 字/秒**。写之前按目标时长反推字数（12 分钟 ≈ 4400 字）。
- 允许口语：`你`、`咱们`、`对吧`。不要书面语感叹词（`值得注意的是`、`综上所述`）。

## 比喻

**整集只用一个核心比喻，贯穿始终。** 暂存区是购物车，那从第一场到结尾都叫它购物车。中途换比喻 = 让观众重新学一遍。

比喻的选取：找一个观众**天天在做**的动作。

- 版本控制 → 游戏存档（存一个档，打输了读档）
- 暂存区 → 超市购物车（挑好了放进去，一起结账）
- 分支 → 平行宇宙（分头做事，最后合并）
- 提交 → 存档点

比喻讲完之后要**补一句官方说法**：「Git 里叫做一次提交」——否则观众看文档时会认不出术语。

## 术语

- **术语第一次出现必须解释**，不能假设观众知道。
- **官方译名如果比俗称难懂，就用俗称。** 例：Git 的 `index` 官方叫「索引」，但对零基础的人讲「暂存区」或「购物车」有效得多。**这种取舍要在交付时明确告诉用户**，因为它是一个有意的准确性让步。
- 英文命令第一次出现时配一句中文解释它干什么，但**命令本身不要翻译**。

## 密度

- 每 2-3 句要有一个「可看见的东西」——一个画面动作、一个例子、一次演示。纯概念讲解连续超过 3 句，观众会走神。
- 数字要具体：「几十万个文件切换版本也就一瞬间」比「非常快」好。
- 不要在一段里塞两个新概念。一个段落只教一件事。

## 实操段落

命令演示要**真的把命令敲出来**（终端打字动画逐字显示），不是直接显示结果。

- 每个命令后面跟一行结果，让观众看到「输入 → 输出」的对应关系。
- 危险命令要给警告。例：`git reset --hard` 会丢掉未提交的修改，必须明确提示。
- 命令演示之外补一句「人话」解释报错怎么办。新手最怕的是报错。
- 结尾给一个**可立即执行的行动**：「现在就找一个你最常用的文件夹，git init 一下」。

## 收尾

最后一场要：
1. 用 3-4 句回顾整集的主线（不是罗列，是串起来）。
2. 给一句能被截图转发的金句。例：「不用背命令。卡住了就敲 `git status`，它会告诉你下一步。」
3. 一个具体的行动号召，而不是「记得点赞」。
