# 技术提案写作

## 概述

将设计拆成范围小、可评审的提案。每份提案只解决下一步必须作出的设计决策：表达清楚，去除不必要的复杂度，明确边界，并以真实用户场景为依据。

好的提案应让评审者能够决策、实现者能够开发、维护者能够验证。文档格式服务于这些目标。

## 使用约定

- 适用于新增提案、现有提案改写、设计评审，以及团队提案格式统一。普通文案润色或无需设计决策的任务清单不必使用此流程。
- 优先遵循用户指定的语言、仓库规范和既有模板；没有要求时，使用用户当前的语言。模板标题可以翻译，API 名称、字段、命令及规范标识保持原样。
- 不绑定编程语言、平台、编辑器或 Agent 工具。示例使用目标项目的语言；尚未确定技术栈时，可使用伪代码、输入输出或行为表。
- 输入可以是想法、问题描述、用户场景、现有提案、代码或规范。先区分已知事实、设计建议、假设和待决问题；不编造用户需求、测试结果、来源或既有共识。
- 仅在信息缺口会改变核心设计时提问。其余缺口在文档中标明假设或列为“待决问题”，并继续完成可确定的部分。
- 改写时保留已确认的语义和约束；评审时给出问题、影响和修改建议。结构或措辞调整不应悄然变更接口契约。
- 按用户要求交付正文、文件或评审意见。撰写提案本身不表示已经批准设计、执行实现或发布变更。

## 核心思路

### 1. 渐进设计

一份提案解决一个明确的设计增量。不要把相关子系统、未来扩展和完整架构全部塞进同一份提案。

相邻决策交给后续提案。优先提出能够独立接受、实现和测试的小范围方案。

### 2. 表达简单直接

选择读者容易理解的表达。如果一个实际示例就能说明设计，先给示例，再给抽象定义。如果一条规则就能解释行为，不要引入多套机制。

设计应简洁、易教、易实现、易记忆。

### 3. 做减法设计

提案应减少重复和非必要复杂度。重点检查能否消除：

- 样板代码
- 手动步骤
- 重复配置
- 暴露给用户的中间机制
- 用户必须记住的特例
- 相似流程中重复的概念

不要为了功能齐全而增加功能。采用能让系统承担重复工作、减轻用户负担的最小设计。

### 4. 明确边界

明确说明：

- 本提案解决什么
- 本提案不解决什么
- 哪些情况有效
- 哪些情况应报错
- 是否改变现有行为
- 当前有哪些替代做法
- 新设计如何与现有机制衔接

边界清楚，才能避免提案扩展成完整系统设计。

### 5. 从多个用户场景中提炼共性

不要直接把单个案例变成新功能。先检查相关用户场景，找出共同需求，再提出能够满足这些场景的最小设计。

如果需求只存在于单一场景，提案就保持相应范围。如果多个场景都缺少同一种表达能力，就直接定义该能力。

## 工作流程

1. 收集推动变更的具体用户场景、示例、缺陷或工作流程。
2. 提炼共同需求，用一句话说明。
3. 找出能够满足该需求的最小设计增量。
4. 将属于后续提案的内容移出本次范围。
5. 用示例、规则和边界定义预期行为。
6. 展示当前替代做法，说明新设计如何减少重复工作。
7. 根据风险补充兼容性、错误处理、备选方案和测试，深度以支持决策为准。

## 模板选择

| 情况 | 使用模板 |
| --- | --- |
| 初步想法、单一行为、对接上游设计或小范围议题 | 简短模板 |
| 需要评审的常规技术变更 | 标准模板 |
| 会形成长期行为约定的语言、API、CLI、协议、架构、数据模型或用户流程 | 完整规范 |
| DSL、查询语言或符号密集的设计 | 完整规范，并补充适用范围和速查表 |

模板的详细程度随风险增加。不要用完整规范包装简单改动；已有团队模板时，将必要信息映射到对应章节，不强制替换标题或编号。

## 简短模板

适用于设计较小、决策点明确的情况。

```md
### 提案

直接说明变更，写出新增行为、API、命令、规则或用户可见结果。

### 背景

解释为什么需要变更。关联相关议题、上游设计、示例、现有行为或用户场景。

### 当前替代做法

说明目前如何解决问题，以及现有做法为什么不足。没有替代做法时写“无”。
```

对于兼容性或引入上游设计的提案，增加：

```md
### 参考依据

链接到上游已接受的设计，用一句话说明对本项目的影响。
```

## 标准模板

适用于大多数提案。示例中的接口形式和章节内容按实际项目调整，不适用的项目应简要说明或省略。

````md
# 提案：<具体变更>

## 1. 摘要

用一段话说明变更内容、适用范围和本次提出的最小设计增量。

## 2. 用户场景与动机

列出具体场景或流程，再说明它们揭示的共同需求。

## 3. 当前替代做法

说明用户目前如何解决问题，以及仍然存在的重复、手动操作或不一致。

## 4. 目标

- 目标 1
- 目标 2
- 目标 3

## 5. 不在本次范围内

- 本提案明确不解决的问题
- 留给后续提案的工作
- 本次不修改的相关系统

## 6. 设计方案

### 6.1 核心规则

说明核心规则或必须保持的约束。

### 6.2 语法、API 或接口

给出面向用户或实现者的准确契约。

### 6.3 用示例定义行为

示例是行为规范的一部分，应足以确定预期结果。

```text
当前形式：……
提议形式：……
等价形式或展开结果：……
```

### 6.4 边界情况

说明有效、无效、省略、冲突和回退等情况。

## 7. 错误处理

| 条件 | 行为 |
| --- | --- |
| 输入无效 | 具体报错行为 |
| 缺少可选依赖 | 警告、跳过或回退行为 |
| 发生冲突 | 是否终止及其错误信息 |

## 8. 兼容性

说明变更属于新增、破坏兼容、主动启用、需要迁移，还是受版本限制；如需迁移，说明路径。

## 9. 备选方案

### 9.1 <方案名称>

说明为什么考虑该方案，以及为什么没有选择它。

## 10. 测试策略

| 测试场景 | 验证方法 |
| --- | --- |
| 正常情况 | 预期结果或断言 |
| 错误情况 | 预期诊断信息 |
| 兼容性情况 | 哪些现有行为必须保持不变 |

## 11. 变更清单

| 范围 | 变更 |
| --- | --- |
| 解析器、API、CLI、界面或文档 | 具体改动 |

## 12. 待决问题（如有）

列出尚未确定且影响评审或实现的决策，不将其写成已确认事实。
````

## 完整规范的补充内容

只增加有助于评审的内容。

| 提案类型 | 补充内容 |
| --- | --- |
| 语言或语法 | 文法、语法展开、类型规则、有效与无效示例、格式化及工具影响 |
| API 或库 | 签名、参数、返回值、副作用、资源所有权、并发和错误模型 |
| CLI 或工具链 | 命令接口、选项、触发时机、执行顺序、路径解析和生成文件 |
| 数据模型 | 结构定义、字段含义、校验、版本演进、迁移和兼容性 |
| 网络或交互协议 | 参与方与交互顺序、消息格式、编码与分帧、状态转换、版本协商、超时、重试与幂等性、错误及兼容性；按风险补充认证、授权和资源限制 |
| DSL 或查询语言 | 适用范围、速查表、核心概念、语法规则、查询示例和实现要点 |
| 架构 | 模块边界、职责归属、依赖方向、全局副作用和回滚路径 |
| 产品流程 | 用户状态、权限、空状态、错误状态、加载状态，以及必要的审计或分析行为 |

引用外部协议、标准或上游设计时，标明名称、版本、相关条款和来源。区分已有规范要求与本提案新增的约定；无法核实的内容列为待确认项。

如需使用规范性关键词，明确“必须（MUST）”“应当（SHOULD）”“可以（MAY）”各自表达的约束强度，并在全文保持一致；声称遵循外部标准时，以该标准的定义为准。

## 写作规则

- 先写本次需要决定的最小问题，再补充必要背景。
- 优先用一条清楚的规则解释行为。
- 将代码示例作为规范：展示当前形式、提议形式、等价或展开形式，以及无效情况。
- 当需求来自实际使用时，先写用户场景，再写抽象动机。
- 用“当前替代做法”证明提案的必要性。
- 非简单变更必须说明“不在本次范围内”的内容。
- 参数、选项、错误、行为组合和变更清单优先使用表格。
- 实现说明应具体到必要的解析器、类型检查器、API、命令、文档或测试。
- 不确定的决策列入“待决问题”，不要悄然固定为结论。
- 避免营销语言和缺乏依据的架构主张。

## 常见问题

| 问题 | 修改方法 |
| --- | --- |
| 试图描述整个系统 | 收窄到下一步设计增量 |
| 从单个案例直接增加功能 | 检查相关场景，提炼共同需求 |
| 示例之前铺陈过多 | 先展示具体行为 |
| 过早引入新机制 | 优先复用或简化已有机制 |
| 缺少边界情况 | 补充有效、无效、冲突和回退示例 |
| 示例只有说明作用 | 让示例明确规定预期行为 |
| 忽略替代做法的实际效果 | 说明仍有哪些重复工作或手动操作 |
| 小改动也写完整规范 | 风险不足以支持完整规范时，使用简短模板 |

## 交付前检查

- 是否只推进一个明确的设计增量？
- 在满足需求的前提下，设计是否足够简单直接？
- 是否减少了重复、手动工作或用户需要记忆的特例？
- 用户场景是否足以证明需求，避免将偶然特例泛化？
- 边界、无效情况和范围外事项是否明确？
- 示例是否准确到能够据此编写测试？
- 是否说明兼容性和迁移要求？
- 是否能在不扩大范围的情况下，将提案转成实施清单？
